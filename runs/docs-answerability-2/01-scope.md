## 2. Claims checked against the code

### 2.1 Verdict grammar (intent: "optional colon after the token; last non-empty line")
**True.** `aveto_support/judge.py` line 44-46: `(?P<id>[^ ]+) (?P<token>ANSWERABLE|NOT_ANSWERABLE):?(?: (?P<reason>\S.*))?` with `fullmatch`, and `parse_verdict` takes `non_empty[-1]` (lines 150-157). Tests assert it (`tests/test_judge.py`, `test_parse_verdict_table` lines 281-339: colon forms 320-330; last-line forms 292-299). Details the spec must state because the intent's one line hides them:
- A colon must be directly after the token and followed by a space and reason or nothing. `ANSWERABLE::`, `ANSWERABLE:reason`, `ANSWERABLE:  reason` (two spaces), `ANSWERABLE.`, bold/backtick wrapping, and `Q1: ANSWERABLE` (colon after the id, which is `WRONG_ID`) all fail closed.
- The reason text, if it contains the string `ANSWERABLE` anywhere, fails (`MULTI_TOKEN`, line 162; the count is over the last line). A reason containing the word in upper case is the case to watch with a model that explains itself.
- **Earlier lines are not entirely ignored.** Any Cc or Cf character in the whole reply (tab, zero-width space, soft hyphen, right-to-left override) other than `\n` and `\r` gives `CONTROL` (line 154), even in a line that is otherwise skipped. The intent says earlier lines are "never shown or stored", which is true; "ignored" would not be. A thought-aloud line with a tab fails the verdict.
- The prompt asks for "at most 12 words of reason"; nothing enforces it (the length cap is 4096 bytes on the whole reply).
- **Open: do the two stage 1 replies parse?** `01-measurement.md` records only a hash of each verdict line and says nothing of whether `parse_verdict` accepts them. The measurement is silent on that and the Architect cannot see the replies. A fresh QA or the stage 4 smoke should say.

### 2.2 Payload layout (intent: "harness prefix, then payload")
`format_judge_input` (lines 112-134) emits `=== Q1 ===`, `Question: ...`, blank, per-file `File n: path`, per-passage `--- passage <rank><letter> | heading: ... | lines a-b ---` ... `--- end passage ---`, then `=== end Q1 ===`. The hash `input_sha256` covers that block only (not the harness prefix). `BLOCK_ID` is the constant `Q1` for every question, so the model's reply can't tell the driver which question it answered; attribution rests on the driver's own run-id bookkeeping and the sha binding in the verdicts file. Security should look at that.

**Prefix length: not measured at stage 1, and Reply 1 D2 is right that 94 is the wrong figure** (94 is the `cliPrefix` system block; `01-measurement.md` line 31). My computation, **not a measurement**: the line `Base directory for this skill: <path>` is 31 characters plus the path of the skill directory. In this worktree the skill directory is `/Users/gopalpatwa/opt/aveto-support/.claude/worktrees/docs-answerability-2/.claude/skills/aveto-judge-seen` (106 characters by my count), giving about 137, against slice 6's 150 in a longer worktree path. Two consequences for the spec: the line is **path-dependent**, so "registered layout" must say the line is whatever the harness writes and report the measured length per run, not a constant; and whether it uses the worktree path or the main checkout path (as `CLAUDE.md` does) must be read from a transcript, not assumed. ### 2.7 How a judge error is counted
Intent: "a failure on both bars, reported as its own number". Code (judge_eval.py 124-146): a `JUDGE_ERROR` verdict is a miss on bar 1 for an unanswerable question (`ok = token == "NOT_ANSWERABLE"`), a miss on bar 2 for an answerable question with the right file in the top five, and **counts on neither bar for an answerable question without a hit**; it is always added to the separate `judge errors` figure. So "a failure on both bars" is true per bar, but an error on a non-hit answerable question is reported only as the number. The Architect should word it so, or change the code and tests. Also: `JUDGE_ERROR` is a valid entry in the verdicts file; nothing in the product produces it (the product gives exit 4 in `judge-apply`).
