# Charter: result-page-clarity

> The only human approval in a Process v2 run. The Orchestrator drafts this file
> at plan confirmation; the human reads it whole and approves it once, in their
> own words, naming this file and its sha256 (`node <playbook>/execution/charter-check.mjs
> runs/result-page-clarity/CHARTER.md` prints both). After that the run proceeds to a
> finished result and **asks nothing**. It stops only when an action is outside
> this Charter (section 9). Every gated action cites the line id that allows it.

## 2. Budget (unit: peak context summed per spawn)
- **C2.1 Plan total:** 400k
- **C2.2 Ceiling:** 720k. Above it the run continues and sends a notice.
- **C2.3 Hard cap:** 800k. Above it the run stops. The run never raises it. The owner gave one number (800k); the ceiling is about 90% of it. Notice 1 is sent when the projection first passes 720k; notice 2 only when spent (not projected) passes 720k, which is 90% of the hard cap. The last UI slice ran 1,570k against a 1,000k plan; the plan total here is the owner's figure for a smaller change, and the ceiling and cap exist for the case it runs over.

## 8. Outcomes decided now
- **C8.1 If a pre-registered check fails:** before the deploy, a failed check or gate (including any C1.4 bar) means no deploy, revision `ca-aveto-ask--0000011` keeps serving, a close-out is written, the run stops. After the deploy, if the new revision fails the live checks (the result heading outside the top 25% at either size, an answer or refusal different from the previous page's, question text in a log table, a kill switch that does not take), or the rollback rehearsal fails (the previous page does not serve, `/health` does not answer, or the roll forward does not restore the new revision), the run keeps or restores the previous revision serving (deploy of image `ffc2e2e5f39a`, or the kill switch on if that fails), reports, and stops; the release fails.
- **C8.2 At the end of a passing run:** push `claude/objective-kapitsa-83d3ae` to origin and open a pull request into `main` with `END_REVIEW.md` linked; set the slice's STATE.md Status to `done` when the pull request opens; never merge (the owner merges; the owner runs the Codex review on the pull request).
- **C8.3 Irreversible actions allowed (rules 1 to 3):** in resource group `rg-aveto-ask` only: build and push one new image from the worktree root with `az acr build -r acravetoaskgp`; deploy the repository's `infra/main.bicep` with `az deployment group create -g rg-aveto-ask` (`deployApp=true`, `killSwitch=off` set explicitly, the existing price and cap values unchanged) three times at most for the release: (1) the new image tag, (2) the rollback rehearsal, which deploys `imageTag=ffc2e2e5f39a` (a new revision of the previous image, as `docs/runbooks/public-ask.md` section 2 says), (3) the roll forward to the new image tag; plus the same command with `killSwitch=on` only if C8.1 requires it. No other resource is added or removed; deleting any resource is not allowed. The branch push and pull request in C8.2. The rollback timing for the release gate is measured from the command to a healthy `/health` on the previous image.
- **C8.4 Human review of a Low-risk change at the end:** review
- **C8.5 Owner positions recorded by this Charter:** the live questions are sent through the real limits, no bypass; their spend counts against C2 as context and against the service's own day share as money; the $10 console limit is unchanged. The owner runs the Codex review on the pull request and merges it; the run does neither.

## 9. Stops (the only reasons the run asks)
1. An action not covered by a line above (a new model, processor, data, file, invariant, or irreversible action), including a needed change to any visitor-facing string.
2. Spend above the hard cap (C2.3).
3. A credential is needed (agents never handle credentials), including an expired `az login`.
4. Lowering a depth in section 7.
5. A change to this Charter (an amendment is a new approval of a new hash).
